# Архитектура

## Запрос к API

Запрос всегда один и тот же и совпадает с методом diff в `zenmoney_lib`:

```
POST https://api.zenmoney.ru/v8/diff/
Authorization: Bearer <API_TOKEN>
Content-Type: application/json

{"serverTimestamp": 0, "currentClientTimestamp": <unix-время>}
```

`serverTimestamp: 0` означает полную копию, поэтому состояние синхронизации хранить не нужно.

## Поток данных

```
расписание, пропущенный запуск или --once
  → блокировка .backup.lock (занята: выход без запроса)
  → удаление остатков прерванного запуска
  → копия за сегодня уже есть и запуск не ручной: выход
  → потоковая загрузка в zenmoney_<время>.json.tmp, подсчёт SHA-256
  → потоковая проверка JSON
  → запись .json.sha256, атомарное переименование в .json, fsync каталога
  → ротация
```

Любая ошибка до публикации завершает запуск: `.tmp` удаляется, существующие копии и ротация не затрагиваются.

## Модули

| Модуль | Ответственность |
|---|---|
| `cli.py` | Аргументы, настройка логов, коды выхода |
| `config.py` | Чтение и проверка переменных окружения |
| `client.py` | HTTP-запрос, запись на диск, повторы |
| `storage.py` | Проверка JSON, имена файлов, публикация, ротация |
| `service.py` | Один запуск: блокировка, порядок шагов, обработка ошибок |
| `scheduler.py` | Расписание, пропущенный запуск, завершение по сигналу |
| `notify.py` | Точка подключения уведомлений |

## Сценарии отказа

| Сценарий | Поведение |
|---|---|
| API недоступен, таймаут | Повторы, затем ошибка запуска |
| Неверный токен (401/403) | Сразу ошибка, без повторов |
| HTTP 429 | Повторы, пауза учитывает `Retry-After`, но не больше 10 минут |
| HTTP 500/502/503/504 | Повторы |
| Прочие коды, включая редиректы | Сразу ошибка. Редирект не выполняется, чтобы токен не ушёл на другой хост |
| Разрыв во время загрузки | Повтор, файл пишется заново |
| Некорректный или пустой JSON | Повтор, затем ошибка запуска |
| JSON без `serverTimestamp` | То же самое: иначе ответ-ошибка с кодом 200 со временем вытеснил бы хорошие копии |
| Нет места, ошибка записи | Сразу ошибка, `.tmp` удаляется |
| Перезапуск контейнера во время загрузки | Блокировку снимает ядро, остаток `.tmp` удаляется при следующем запуске |
| Несколько одновременных запусков | Второй запуск завершается без запроса к API |
| Ошибка удаления старой копии | Записывается в лог, бэкап остаётся успешным, следующая ротация повторит удаление |

При остановке контейнера загрузка прерывается между чанками, а `.tmp` удаляется. Если соединение зависло дольше `stop_grace_period`, Docker завершит процесс принудительно, и `.tmp` удалится при следующем запуске.

## Решения

**`zenmoney_lib` не используется как зависимость.** Её клиент читает весь ответ в память через `response.json()`, а ответ может достигать 1 ГБ. Модель `Diff` к тому же пересобирает данные и может потерять неизвестные поля. Сервис берёт только контракт запроса и сохраняет байты ответа без изменений.

**Сигналы принимаются через `sigwait`.** Python с PID 1 игнорирует SIGTERM без обработчика, а вызов `Event.set()` из обработчика сигнала может привести к взаимной блокировке.

**Блокировка через `flock`.** Она работает и между потоками планировщика, и с отдельным процессом `--once`. Ядро снимает её при падении процесса, поэтому зависшей блокировки не остаётся.

**Порядок записи: сначала `.sha256`, потом `.json`.** Копия не появляется без контрольной суммы. Падение между двумя переименованиями оставит лишь маленький `.sha256` без пары, он ни на что не влияет.

**Свободное место заранее не проверяется.** Размер ответа заранее неизвестен, поэтому сервис обрабатывает ошибку ENOSPC при записи.

## Уведомления

Все окончательные сбои проходят через `notify_failure(message)` в `notify.py`. Чтобы отправлять их в Telegram или webhook, добавьте отправку в эту функцию и читайте настройки из окружения. Ошибку самой отправки нужно перехватывать, чтобы она не ломала работу планировщика. Текст сообщения не содержит токен.
